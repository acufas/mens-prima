# ADR-0001: Shared matrix shape validation and zero-column `matvec` semantics

- Status: Accepted
- Date: 2026-11-25
- Context: `nn_numerics.py` (`dot`, `matvec`), the foundation of a numerical library

## Context

Two related defects were identified in `matvec`. Both stem from the same
underlying issue: `matvec` had no explicit notion of *shape*, so edge cases
fell out of incidental control flow rather than a stated contract.

The original implementation was:

```python
if not len(matrix) or not len(vector):
    return []
if len(matrix[0]) != len(vector):
    raise ValueError('Unequal inner dimensions between matrix and vector!')

return [dot(row, vector) for row in matrix]
```

### Problem 1: The `n = 0` edge case

For completeness, when `n = 0`, the matrix-vector implementation still
iterates over the `m` rows. A more general time complexity covering that
edge case is `O(1 + m(n+1))`, rather than the `O(m * n)` originally stated
in the performance profile.

The problem was worse than a complexity footnote — the behaviour was
incorrect. The early return `if not len(matrix) or not len(vector)` conflates
two different situations:

- `m = 0` (`matrix == []`): returning `[]` is correct.
- `n = 0` with `m > 0` (`matrix == [[], [], []]`, `vector == []`):
  mathematically this is a 3x0 matrix times a 0-vector, which should give
  `[0.0, 0.0, 0.0]` — one zero for each row. The original code returned `[]`,
  silently dropping the rows.
- Worse, `matvec([[1, 2]], [])` also returned `[]` instead of raising a
  dimension mismatch.

NumPy adopts the convention that a `(3, 0)` matrix multiplied by a `(0,)`
vector yields `array([0., 0., 0.])`, so this ADR adopts NumPy's shape
semantics as the specification.

The complexity formula `O(1 + m(n+1))` follows naturally once the
short-circuit is removed: setup is `O(1)`, and each of the `m` rows costs
one `dot` call overhead plus `O(n)` work. Note that FLOPs stay `2mn` — at
`n = 0` zero arithmetic is performed, but `m` loop iterations are still
paid, which is why the time formula needs the extra term while the FLOP
count does not.

### Problem 2: Jagged (ragged) matrix handling

Input validation correctly rejects ragged matrices, although it does so
indirectly through `dot()`.

Consider:

```python
matrix = [[1, 2], [3]]
vector = [1, 1]
```

The first row passes the initial dimensional check. When the list
comprehension reaches the second row, `dot()` raises a `ValueError`.

This satisfies the requirement, but has minor limitations:

- Malformed matrices may be partially processed before being rejected.
- The resulting exception describes unequal vector lengths rather than an
  irregular matrix.

There is no compelling reason to change this for the current project in
isolation: since `matvec` is pure, the "partial processing" has no
observable side effects — the half-built list is discarded. The only real
cost is the misleading error message. However, this stops being acceptable
if a later implementation adds logging, parallelism, or a GPU/blocked path
where partial work matters. Since this library is intended as a foundation
for further numerical operations, the validation logic was expected to be
needed again.

## Options considered

### Option A: Keep delegating validation to `dot` (status quo)

Zero extra code. Correct rejection of ragged matrices, with the limitations
described above: partially processed input and a misleading exception
message.

### Option B: One upfront validation pass in `matvec`

Check every row's length before any arithmetic:

```python
if not matrix:
    return []
n = len(matrix[0])
for i, row in enumerate(matrix):
    if len(row) != n:
        raise ValueError(f"Ragged matrix: row {i} has {len(row)} columns, expected {n}")
if n != len(vector):
    raise ValueError(...)
return [dot(row, vector) for row in matrix]
```

This gives fail-fast behaviour and an error that names the offending row.
The validation pass costs `O(m)` calls to `len`, which is negligible next
to `O(mn)` arithmetic for `n >= 1` — and at `n = 0` it *is* the `O(m)`
term from the complexity formula, so the complexity accounting stays
honest.

### Option C: A shared shape helper (chosen)

A single helper, `_shape(matrix) -> tuple[int, int]`, returns `(m, n)` or
raises for ragged input. `matvec` uses it now; future operations
(`matmul`, `transpose`, matrix addition, and so on) reuse it instead of each
re-implementing ragged checks. This is Option B, factored so the validation
logic lives in exactly one place (DRY).

## Decision

Adopt Option C.

`nn_numerics.py` gains a private helper:

```python
def _shape(matrix: list[list[float]]) -> tuple[int, int]:
    """Return the (rows, columns) shape of a matrix.

    Raises ValueError if the matrix is ragged.
    """
    if not matrix:
        return (0, 0)
    n = len(matrix[0])
    for i, row in enumerate(matrix[1:], start=1):
        if len(row) != n:
            raise ValueError(f"Ragged matrix: row {i} has {len(row)} columns, expected {n}")
    return (len(matrix), n)
```

`matvec` is rewritten to use it, which fixes the `n = 0` cases as a side
effect of removing the old short-circuit:

```python
m, n = _shape(matrix)
if m == 0:
    return []
if n != len(vector):
    raise ValueError(f"Unequal inner dimensions: matrix has {n} columns but vector has length {len(vector)}")

return [dot(row, vector) for row in matrix]
```

The performance profile for `matvec` now states time complexity
`O(1 + m * (n + 1))`, and its docstring spells out the empty and
zero-column semantics.

### Shape semantics adopted

| Input | Result |
| --- | --- |
| `matvec([], vector)` for any `vector` | `[]` |
| `matvec([], [])` | `[]` |
| `matvec([[], [], []], [])` (a 3x0 matrix) | `[0.0, 0.0, 0.0]` |
| `matvec([[]], [1])` (0 columns vs length-1 vector) | `ValueError` |
| `matvec([[1, 2]], [])` (2 columns vs empty vector) | `ValueError` |
| Ragged matrix, e.g. `matvec([[1, 2], [3]], [1, 1])` | `ValueError: Ragged matrix: row 1 has 1 columns, expected 2` |

### Subsidiary decisions

- `_shape([])` is defined as `(0, 0)`. An empty matrix has no defined
  number of columns, so `matvec` special-cases `m == 0` and returns `[]`
  for any vector. This preserves the previously tested behaviour
  (`matvec([], [1, 2]) == []`); it is now a decision rather than an
  accident.
- Error precedence: if a matrix is both ragged and mismatched with the
  vector, raggedness is reported first, because it is a defect intrinsic to
  the matrix, independent of the vector.
- Keep raising `ValueError`, with a more informative message, rather than
  inventing a custom exception type. Existing callers and tests already
  expect `ValueError`; a richer exception hierarchy can be introduced later
  if a caller ever needs to distinguish the cases programmatically.
- `_shape` is private (underscore-prefixed). It is shared within the
  library, not yet part of the public API.

## Testing

Following red/green development, tests were written first and confirmed to
fail before the implementation change. New coverage includes:

- A `TestShape` test class pinning the helper's contract directly: empty
  matrix `(0, 0)`, square, non-square, zero-column, single-element, and
  ragged input raising with the expected message.
- Strengthened jagged-matrix tests asserting the exact error message with
  `assertRaisesRegex`, covering a short row, a long row, a short first row,
  an empty first row, and raggedness taking precedence over a vector
  dimension mismatch.
- Zero-column and empty-vector behaviour: `matvec([[], [], []], [])`
  returns `[0.0, 0.0, 0.0]`, `matvec([[]], [1])` raises,
  `matvec([[1, 2]], [])` raises, and `matvec([], [])` returns `[]`.

Verified behaviour after the change:

```text
matvec([[], [], []], [])      -> [0.0, 0.0, 0.0]
matvec([], [1, 2])            -> []
matvec([[1, 2], [3]], [1, 1]) -> ValueError: Ragged matrix: row 1 has 1 columns, expected 2
matvec([[1, 2]], [])          -> ValueError: Unequal inner dimensions: matrix has 2 columns but vector has length 0
```

The full test suite passes (62 tests at the time of this ADR).

## Consequences

Positive:

- The `n = 0` case is now mathematically correct (NumPy-compatible)
  instead of silently discarding rows.
- Ragged matrices are rejected before any arithmetic, with an error
  message that identifies the offending row and the expected column count.
- Shape validation exists in exactly one place and can be reused by every
  future matrix operation, instead of being re-implemented (or, worse,
  re-delegated to `dot`) per operation.
- The stated time complexity, `O(1 + m(n+1))`, now accounts for the
  per-row overhead that dominates when `n = 0`.

Negative / costs:

- `matvec` pays an additional `O(m)` validation pass per call. This is
  negligible relative to `O(mn)` arithmetic for `n >= 1`, but it is real
  overhead in a hypothetical hot loop that calls `matvec` repeatedly on
  already-validated data.
- The ragged-matrix error message reads "1 columns" in the singular case;
  pluralisation was deliberately left alone rather than adding branching
  to a format string.

Deferred:

- Validation on every call is the simple, safe default. Libraries such as
  NumPy avoid repeated validation by making the array a *type* whose shape
  invariant is established once at construction, so operations can trust
  it. A small validated `Matrix` type would be the eventual evolution of
  `_shape` if repeated validation ever becomes a measurable cost. That is
  explicitly out of scope for now (YAGNI) until `matvec` has sibling
  operations that would otherwise duplicate the checks.
